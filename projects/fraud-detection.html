Fraud Detection System

An end-to-end system that scores card transactions for fraud risk and explains every prediction. XGBoost is trained on 590,540 real transactions and served through a FastAPI backend with SHAP explanations and an analyst dashboard.

The problem

Fraud is rare: 3.5% of transactions in this dataset. A model that always answers "not fraud" would be 96.5% accurate and catch nothing, so accuracy is the wrong measure. The model has to rank risky transactions above normal ones, and an analyst reviewing a flagged payment needs to see why it was flagged.

Data

The IEEE-CIS Fraud Detection dataset: 590,540 card transactions with a transaction table and an identity table, 434 raw columns, many of them anonymised. Exploration found strong signals: purchasers with mail.com addresses had a 19% fraud rate, product code C 11.7%, and Discover cards 7.7%, against a 3.5% baseline.

Approach

  1. Clean and merge. Joined the two tables, cut memory from 2.5 GB to 1.68 GB by downcasting types, dropped 12 columns with more than 90% missing values and filled the rest.
  2. Engineer features. Hour, day and week from the transaction clock, a log-scaled amount, flags for high-risk email domains and card types, and the 20 most informative of 339 anonymised features: 106 features in total.
  3. Handle the imbalance without leakage. Stratified 80/20 split first, label encoders fitted on training data only, then SMOTE on the training set only, so nothing from the test set influences training.
  4. Train and compare. XGBoost and LightGBM with early stopping. XGBoost won and was explained with SHAP TreeExplainer.

Results

AUC-ROC measures ranking quality across all thresholds, which suits a review queue where analysts start from the riskiest payments. It is not a promise of real-world performance: fraud patterns drift over time, and the dataset is a fixed historical sample.

The API and dashboard run in one Docker container on Render. A Pytest suite and a Docker smoke test run in GitHub Actions on every push.

A bug worth finding. While polishing the project I found that card and email inputs were silently ignored at prediction time, because the training categories had been encoded twice. I rebuilt the original mapping, fixed the API and added a regression test so it cannot return.

Limitations

  • Many strong features in the dataset are anonymised, so the demo form can set only the human-readable inputs; the rest use typical values.
  • The model is trained on one historical dataset and would need monitoring and retraining for live traffic.
